# Troubleshooting

| Problem | Solution |
|---|---|
| `ConfigError: unknown key(s) [...]` on profile load | The profile YAML has a typo'd or removed key. `config/loader.py::_section_from_dict` rejects unknown keys on purpose (a silently-ignored ablation flag is worse than a startup error) -- fix the key name, don't suppress the check. |
| `ConfigError: ... seed range must not overlap` | `scenario.{train,validation,test}_seed_range` overlap. Ranges must be disjoint (section 31's non-negotiable). |
| `ModuleNotFoundError: drl_agent_interfaces` (or `rclpy`) | You're running outside the sourced ROS2 environment. `source /opt/ros/humble/setup.bash && source ros2_ws/install/setup.bash` first, or run only the ROS-free `tests/` suite, which needs neither. |
| `tests/test_tqc_parity.py` skipped | Either torch isn't installed (expected on a bare host -- run inside the Docker container) or this package was copied out of the monorepo so the sibling `drl_agent` checkout isn't at the expected relative path; the test skips cleanly rather than failing in that case. |
| `RuntimeError: no feasible layout found for seed=...` from `generate_scenario` | `scenario.max_obstacles` is too dense for `scenario.world_size_m` at that robot radius. Lower `max_obstacles` or raise `world_size_m`. |
| Environment node hangs waiting for `/reset` | Gazebo isn't running yet, or `SetEntityPose`'s service (`/world/<world_name>/set_pose`) doesn't match the launched world's actual name -- check `-p world_name:=` matches the `hunter_se_gazebo` launch argument. |
| `filtered_cmd_v_mps=0` in the (future) CSV logger | Same known false-read documented in the main repo's CLAUDE.md for drl_agent -- not specific to this package. |
| Colcon build fails on `drl_agent_interfaces not found` | Build it first (or together): `colcon build --packages-select drl_agent_interfaces hunter_kinodynamic_rl`. |
| `/reset` or `/step` hangs, then `pause_world`/`set_pose` times out after `gz_service_call_timeout_sec` and the node exits | **Root cause (found + fixed via live Gazebo testing):** if the Gazebo service CLIENTS (`world_control_client`, `set_entity_pose_client`, ...) share the SAME `MutuallyExclusiveCallbackGroup` as the service SERVERS (`/reset`/`/step`), a server callback that blocks polling a client future can never let the executor run that client's own response callback — permanent self-deadlock. Fixed in `environment_node.py` by giving the Gazebo clients their own dedicated callback group (mirrors drl_agent's `clients_callback_group` split). If you add a NEW Gazebo service client, put it in that same dedicated group, never the servers' group. |
| `ros_gz_interfaces` world services not found at `/world/drl_arena/...` | Every `hunter_se_gazebo` world's SDF declares `<world name="default">` regardless of the world FILE's own name (`drl_arena.world`, `hospital.world`, ...) — the actual services are always `/world/default/{control,set_pose,create,remove}`. `environment_node.py`'s `world_name` parameter AND `launch/environment.launch.py`'s own `world_name` launch argument both default to `"default"` for exactly this reason (section P1-1: the launch file's default previously silently overrode the node's own correct default back to `"drl_arena"` — fixed, live-verified with `ros2 launch hunter_kinodynamic_rl environment.launch.py profile:=smoke_test` and no `world_name:=` override); only override it if a world's SDF genuinely uses a different `<world name>`. |
| `/scan`/`/odometry` never arrive (any node, not just this package's) despite Gazebo/bridges clearly running and topics correctly matched (`ros2 topic info --verbose` shows the subscription) | The Gazebo WORLD is paused (`/world/<world_name>/control`'s `pause` state) — sensor/odometry plugins don't publish while paused, but `/clock` may still tick. Commonly left over from an environment_node (or any other client) being killed abruptly mid-`/reset`/`/step` (which pauses the world as part of its own sequencing) rather than exiting cleanly. Fix: `ros2 service call /world/<world_name>/control ros_gz_interfaces/srv/ControlWorld "{world_control: {pause: false}}"`. A node built on this package's safety pattern (`real_policy_node.py`) correctly falls back to publishing a safe stop while starved like this — a paused world is a Gazebo/testing-environment issue, not something app code should need to detect. |
| `FileNotFoundError: <checkpoint_dir>/<name>.pt` (or `.json`) from `evaluation_node.py`/`real_policy_node.py`/`train_node.py` resume, after upgrading past the 2026-08-25 checkpoint rewrite (item 3) | The checkpoint layout changed: `<checkpoint_dir>/<name>` is now a DIRECTORY (a symlink to `.generations/<uuid>/` containing `model.pt`/`manifest.json`/`replay.npz` together), not flat `<name>.pt`/`<name>.json` sibling files — see `rl/checkpointing/manager.py`'s module docstring. A checkpoint saved by an OLDER (pre-item-3) session must be read via the explicitly-named `manager.load_legacy_flat(directory, filename, components)` instead of the default `load_generation` — there is no silent auto-detection between the two layouts, by design. |
| `RuntimeError: checkpoint generation mismatch at <path>: model.pt embeds generation=... manifest.json records generation=... replay.npz embeds generation=...` | One of the checkpoint's three files (`model.pt`/`manifest.json`/`replay.npz`) was replaced independently of the other two — e.g. a manual file copy/swap, or a partially-completed manual edit. This is the intended, correct failure mode (item 3): the three files are cross-verified on every `load_generation` call precisely so a mismatched set is never silently loaded. Fix: restore the matching set for ONE generation (all three files from the SAME `.generations/<uuid>/` directory), never mix files from different generations. |
| `SystemExit: ... live environment_node's architecture_fingerprint_sha256=... does not match checkpoint's own ...` from `evaluation_node.py` | The live `environment_node` and the checkpoint's own training config report the SAME profile NAME but a DIFFERENT resolved architecture (item 2) — e.g. the profile YAML was edited after the checkpoint was trained, or the wrong profile file is on disk under that name. Relaunch `environment_node.py` with the EXACT profile the checkpoint was actually trained under (`checkpoint_dir>/<name>/manifest.json`'s own `resolved_config`/`profile_name` is authoritative, never trust the live YAML file's current content). |
| `real_policy_node.py -p inference_worker_mode:=process` (or `runtime.inference_worker_mode: "process"` in a profile) takes several seconds longer to become ready than thread mode | Expected (item 5): `'process'` mode spawns a genuinely SEPARATE OS process via `multiprocessing`'s `'spawn'` start method (never `'fork'` — rclpy's own DDS threads make `fork()` deadlock-prone), which re-imports this whole package and reloads the checkpoint from scratch in a fresh interpreter. `InferenceWorkerProcess.__init__`'s `ready_timeout_sec` (default 60s) exists precisely to accommodate this; a genuinely stuck worker process is still forcibly restarted after `runtime.inference_worker_max_consecutive_timeouts` consecutive per-tick timeouts, not left waiting forever. |
| `RuntimeError: generate_scenario: dynamic obstacle radius=... leaves no inset room in a world_size_m=... world` | `scenario.world_size_m` is too small to inset a dynamic obstacle's own 0.3m radius from the world boundary at all (item 7 — mirrors the identical pre-existing check for the robot's own start/goal inset). Raise `world_size_m`, or disable/reduce `scenario.dynamic_obstacle_count` for that profile. |
| A benchmark comparison across two checkpoints looks unfair / one model gets more episode steps than another | Check `evaluation.max_episode_steps` in each evaluation profile explicitly (item 1) — this is now the SOLE episode-length cutoff, on BOTH the client (`run_episode`'s loop bound) and the live server (`environment_node.py`'s own `/step` timeout during a fixed-benchmark episode, round-2 fix). A checkpoint's own `training.episode_length_steps` (its TRAINING profile, frozen in its manifest) is never consulted for benchmark evaluation, on either side. Two evaluation profiles used to compare models on "the same" benchmark must set identical `max_episode_steps` (and generally identical `evaluation`/`reward`/`scenario`/`runtime` sections — compare their `evaluation_contract_fingerprint`, recorded in each run's `run_metadata`/`summary.json`, to verify this directly from the result files). |
| `SystemExit: ... live environment_node's evaluation_contract_fingerprint_sha256=... does not match ... REQUESTED effective evaluation-contract fingerprint ...` from `evaluation_node.py` (round 2) | The live environment did not actually apply the evaluation-contract override `evaluation_node.py` pushed to it — e.g. `environment_node.py` predates the round-2 `evaluation_contract_override_path` mechanism (rebuild + relaunch it), or the override YAML `evaluation/contract_override.py::write_evaluation_contract_override` wrote was malformed/rejected. This is a DIFFERENT check from the `architecture_fingerprint_sha256` mismatch above -- that one verifies the checkpoint's network shape; this one verifies world size/reward/runtime/timeout/common-metrics (the benchmark CONDITIONS) are actually what was requested, not what the live environment's own launch-time profile happened to set. |
| `RuntimeError: generate_scenario: no feasible layout found` (or the whole test process appears to hang / spin at high CPU) when calling `generate_scenario`/triggering procedural generation with an unusually LARGE `scenario.world_size_m` | The occupancy-grid reachability check (`is_reachable`) allocates an `O((world_size_m/0.25)^2)` boolean grid and BFS-floods it -- a world size in the hundreds of meters (e.g. accidentally set while testing an evaluation-contract override) makes this genuinely slow/CPU-heavy, not hung. Keep `world_size_m` in the same order of magnitude as the shipped profiles (single-digit to low-double-digit meters) unless you specifically intend to stress-test the generator; for evaluation-contract testing that doesn't care about procedural placement, use a `scenario_override_path` (exact fixed scenario) instead so procedural generation never runs at all. |
| `SystemIdRecorder`'s "stop" trial reports a `stopping_distance_m`/`stopping_time_sec` that looks too LARGE (visibly includes some pre-braking travel) | Confirm `system_id_node.py` is rebuilt/up to date -- the round-2 fix snapshots the robot's REAL (x, y, v, steering) directly from live odometry AT the instant the brake command is issued (`SystemIdRecorder._stop_trial_brake_onset_state`), passed to `analyze_stop_test` as `brake_onset_state`. If you're reprocessing an OLDER recorded CSV that has no such snapshot (only `brake_onset_t_sec`), the fallback EXTRAPOLATES the last pre-onset sample forward to the exact onset instant at its own steady-state velocity (`_extrapolate_forward_at_constant_velocity`) rather than anchoring at the (earlier) sample's own timestamp -- if the gap between the last pre-onset sample and `brake_onset_t_sec` exceeds `max_sample_gap_sec`, the trial is now correctly rejected (`reason="onset_reference_gap_too_large"`) instead of silently using a stale reference point. |
| `SystemExit: ... live environment_node is running profile='<a full path>', but this checkpoint was trained under profile='<a short name>'` from `evaluation_node.py`, even though the live environment_node WAS relaunched with the checkpoint's own exact training profile (round 5) | Rebuild -- `validate_live_environment` previously compared the live node's RAW `profile` ROS parameter (its literal launch-time CLI string) against the checkpoint manifest's RESOLVED profile name; `load_profile` strips any PATH down to `os.path.splitext(os.path.basename(...))[0]` before it becomes `Profile.name`/a manifest's `profile_name`, so the two only coincided when a profile was launched by short registered NAME on both occasions, not by an explicit path (a documented, supported `load_profile` mode -- e.g. an ad-hoc profile living outside `config/profiles/`). Fixed: `environment_node.py` now exposes `resolved_profile_name` (`self.profile.name`), and `evaluation_node.py` compares against that instead of the raw `profile` parameter -- a path-launched profile now compares correctly against a path-launched checkpoint. |
| A real-rclpy integration test (e.g. in `tests/test_system_id_node.py`) fails with a value that looks like it came from a DIFFERENT, unrelated live robot/sim rather than the test's own synthetic publisher | Check for a STALE live Gazebo/`ros_gz_bridge`/`environment_node.py` process still running and publishing to the SAME topic name the test's synthetic publisher uses (`/odometry`, `/hunter_se/joint_states`, etc.) -- `ros2 node list`/`ros2 topic list` show it, even a fully orphaned zombie process (its own Gazebo backend long dead) can keep publishing stale cached values. `pkill -9 -f "ign gazebo|gz sim|ros_gz_bridge|environment_node.py|hunter_se_cmd_prefilter"` then `ros2 daemon stop && ros2 daemon start` (the daemon caches discovery info and won't refresh `ros2 topic list` on its own) before re-running the suite. This is an environment-hygiene issue, not a test or package defect -- a long-lived Docker container used across many sessions/rounds can accumulate these for days if a Gazebo launch was ever killed abruptly (`kill $PID` on `ros2 run`'s WRAPPER only, since it forks rather than execs, is a common way to leave the actual node process as such an orphan). |
