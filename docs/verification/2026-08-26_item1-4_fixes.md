## item-1: Gazebo physics-step reality-check

**Root cause.** `RUNTIME_FIELDS_FIXED_AT_LAUNCH` (environment_node.py) only
ever compared two DECLARED config numbers against each other (an
evaluation-contract override's requested `gazebo_max_step_size_sec` vs.
this process's own launch-time value) -- neither side was ever checked
against the connected Gazebo world's REAL SDF `<max_step_size>`.
`multi_step_advance`'s own confirmation loop
(`while observed_dt < (expected_dt - eps): sleep`) only ever rejected an
UNDER-step; an OVER-step made the loop condition false on the very first
check and returned immediately as if correct. Missing `/clock` degraded to
a logged warning + an unverified `nan` return instead of failing.
`nan`/backward-moving `/clock` readings were never checked at all.

**Fix.**
- `RuntimeConfig.physics_step_tolerance_sec` (new, default `0.005`s) --
  `config/schema.py`.
- `multi_step_advance` (`env/simulation/gazebo_runtime.py`): symmetric
  `abs(observed_dt - expected_dt) <= tolerance` check (rejects both
  under- and over-step); fails fast (before even issuing the service call)
  on missing `/clock`; fails fast on NaN (before stepping AND mid-step);
  fails fast (not after a full timeout) on a backward-moving clock.
- `GazeboRuntimeMixin.verify_physics_step_calibration` (new): a real
  `multi_step[1]` + `/clock` probe against `runtime.gazebo_max_step_size_sec`.
  `propagate_state` runs it exactly once, lazily, before the FIRST
  deterministic-stepping advance of a process's lifetime -- deterministic
  evaluation genuinely never advances physics until this has passed.
  Result cached (`_physics_step_calibrated`/
  `_physics_step_calibration_observed_dt_sec`) and exposed as ROS
  parameters (`physics_step_calibration_verified`/
  `physics_step_calibration_observed_dt_sec`) for a remote reader.
- `evaluation_node.py::augment_summary_with_physics_calibration`: after
  `run_benchmark` returns, re-reads those two parameters from the live
  environment and re-writes `summary.json` with them -- a
  deterministic-stepping run's result file records whether physics was
  ACTUALLY verified, never merely assumed from the profile's own
  declaration.
- **A second, real bug found BY doing the live check below** (not
  theorized in advance): `multi_step_advance`'s `ControlWorld.Request()`
  never set `world_control.pause` -- `ros_gz_interfaces/WorldControl.pause`
  defaults to `False`, and Ignition's `ControlWorld` handler treats an
  explicit `pause=False` accompanying `multi_step` as "leave the world
  UNPAUSED afterward". Every `multi_step_advance` call before this fix
  silently left the world free-running (`real_time_factor=1.0`) after each
  deterministic step. Fixed by explicitly setting
  `req.world_control.pause = True` in the same request.

## item-2: system-ID stale-data handling

**Root cause.** `_run_one_trial`'s "stop" branch called
`analyze_stop_test(samples, brake_onset_t_sec=..., brake_onset_state=...)`
even when `build_brake_onset_snapshot` had explicitly returned
`(None, "<reason>")` (odometry/joint-state stale, missing, or an
inconsistent receipt time) -- since `brake_onset_t_sec` was still passed,
`analyze_stop_test`'s OWN, separately-audited, but STRICTLY LOOSER
sample-extrapolation fallback (intended for OFFLINE CSV reprocessing, which
has no live receipt-time concept at all) silently re-validated the trial as
`valid=True`.

**Failing repro (before fix):**

```python
from hunter_kinodynamic_rl.dynamics.system_identification import Sample, analyze_stop_test
# dense sample stream around onset=1.0s (would satisfy the sample fallback)
result = analyze_stop_test(samples, brake_onset_t_sec=1.0, brake_onset_state=None,
                            initial_speed_target_mps=2.0)
# BUG REPRO: {'valid': True, 'reason': None, 'stopping_distance_m': 0.35, ...}
```

**Fix.** `analyze_stop_test` gained
`brake_onset_snapshot_failure_reason`/`allow_fallback_despite_live_snapshot_failure`
(`dynamics/system_identification.py`). When a live caller's failure reason
is provided and no `brake_onset_state` was recovered, it now returns
`valid=False` with that SAME reason immediately -- never reaching the
sample-extrapolation fallback -- unless the caller EXPLICITLY opts back in
(`allow_fallback_despite_live_snapshot_failure=True`), in which case the
result is tagged `estimated=True`/
`reference_source="sample_extrapolation_despite_stale_live_snapshot"`.
Offline-CSV callers that never pass this reason (the only call site that
does is the live `SystemIdRecorder` path) are byte-identical to before.
`system_id_node.py::_stop_trial_result` (new, factored out of
`_run_one_trial` for testability) passes
`node._stop_trial_brake_onset_invalid_reason` through.

## item-3: checkpoint-prune safety

**Root cause / fixes**, all in `rl/checkpointing/manager.py`:
- **No concurrency protocol at all.** Added `PruneAlreadyRunningError` +
  a directory-level exclusive, non-blocking lock (`.prune.lock`) that
  `prune_orphan_generations` must acquire for its ENTIRE run -- a second
  concurrent call against the SAME directory is rejected outright, not
  raced.
- **TOCTOU between the final "referenced?" check and `rmtree`.** Replaced/
  augmented with a REAL exclusive, non-blocking lock acquisition on each
  candidate generation's own `.lock` file immediately before deletion --
  the SAME file `load_generation` now holds a SHARED lock on for the
  ENTIRE duration of its read. The two are atomic with respect to each
  other at the OS level; prune simply skips (never deletes, never blocks)
  a generation it can't lock.
- **`.orphaned_since` fsync gaps.** Every create/update/removal of the
  marker now also fsyncs its own generation directory; `.generations`
  (the parent) is fsynced after any real deletion.
- **`shutil.rmtree(..., ignore_errors=True)`.** Replaced with a real
  try/except: a genuine failure is collected (never silently "deleted"),
  and if any candidate failed, `PrunePartialFailureError(deleted, failed)`
  is raised at the end -- `.deleted` contains ONLY generations that
  actually disappeared from disk.

**Failing repro.** The pre-fix source (read in full before editing, see
conversation) had zero locking primitives (no `fcntl` import at all) and
`shutil.rmtree(gen_dir, ignore_errors=True)` with no failure tracking --
by construction, every new regression test below fails against it
(a concurrent prune would race unimpeded; a load-in-flight generation
would be deleted out from under it; an `rmtree` failure would silently
report as deleted). Re-verified directly: `git stash push -- manager.py`
(reverting to the pre-edit, un-committed content) + rerunning the new
tests reproduced import-level unavailability (the file didn't exist yet
at `HEAD` at all, since it's a new, uncommitted file) -- confirming there
was no committed "old" version to A/B against beyond the source already
read in full during this session; the stash was immediately popped to
restore the fix (`git stash pop`), and the full suite was re-run clean
afterward (37/37 `test_checkpointing.py`, 741/741 overall) to confirm no
side effects from the stash round-trip.

**Passing after fix:**

```

# 37 passed
```

New tests: `test_prune_already_running_raises_and_deletes_nothing`,

## item-4: evaluation-contract restore failure propagation

**Root cause.** `_restore_launch_time_evaluation_contract` only ever
`print()`ed a WARNING and returned `None`; `main()`'s `finally` block
discarded that return value entirely. A benchmark run whose evaluation
BODY succeeded but whose POST-RUN contract restoration failed (rejected
parameter-clear, a `/reset` that raised, or a fingerprint mismatch) still
exited 0 -- indistinguishable, to a caller checking only the exit code,
from a genuinely clean run.

**Fix** (`nodes/evaluation_node.py`):
- `_restore_launch_time_evaluation_contract` now returns a structured
  `RestoreResult(ok, reason, restored_fingerprint)` (same WARNING prints
  as before, for the existing tests that assert on them; never raises,
  so it still can't mask an in-flight exception from the try body it
  cleans up after).
- `_write_contract_restore_status`: persists the result as a durable
  `contract_restore_status.json` artifact next to `summary.json`.
- `run_eval_body_with_contract_restore` (new, factored out of `main()`'s
  former inline try/finally so the ORCHESTRATION pattern itself is
  directly unit-testable): runs `body(state)`; in `finally`, restores if
  an override was applied; AFTER the try/finally completes (i.e. only
  when `body` did NOT raise), raises `SystemExit` if restoration failed.
  An exception from `body` itself always propagates unmasked -- the
  post-finally check is structurally unreachable in that case.

**Failing repro (conceptual, confirmed by reading the pre-fix source in
full):** `main()`'s `finally` block called
`_restore_launch_time_evaluation_contract(...)` and discarded its return;
no code path after it could ever `sys.exit`/`raise` on a restoration
failure when the try body itself hadn't raised -- the process fell
through to the end of `main()` and exited 0 regardless.

**Passing after fix:**

New tests: `test_restore_returns_ok_{true_on_a_clean_restore,false_on_rejected_parameter_clear,false_when_reset_raises,false_on_fingerprint_mismatch}`,
`test_body_success_and_restore_failure_raises_systemexit_not_exit_zero`

## Limitations (genuinely not done in this pass)

- **No full SAC/TQC training+evaluation E2E smoke rerun against live
  Gazebo with `deterministic_stepping: true`.** No shipped profile
  currently enables `runtime.deterministic_stepping` (it remains an
  opt-in mechanism no production profile has adopted yet), and standing
  up a full multi-minute training+checkpoint+evaluation cycle live was out
  of scope for a defect-verification pass measured in hours, not a full
  research run. What WAS live-verified: the calibration PRIMITIVE itself
  (`verify_physics_step_calibration`/`multi_step_advance`) against a real
  running world, through the real `KinodynamicEnvironmentNode` code path,
  under a real `MultiThreadedExecutor` -- including finding and fixing a
  genuine bug (`pause=True`) that only surfaced under live testing.
- **No second Gazebo world with a genuinely different `<max_step_size>`.**
  Both shipped worlds (`empty.world`, `drl_arena.world`) declare
  `0.001`s. The "expected 0.1s/actual 0.2s"-style mismatch was
  demonstrated live via a deliberately WRONG declared
  `gazebo_max_step_size_sec` against the SAME real world (CASE 2 above) --
  physically equivalent evidence for the code path under test (the
  observed-vs-declared mismatch is what's being verified, not which side
  is "the world's fault"), but not a literal second-SDF-file run.
- **`checkpoint-prune` power-loss durability** is verified at the
  fsync-call level (the tests confirm `_fsync_path` is actually invoked
  against the right paths at the right times -- see item-3), not via an
  actual kill -9-mid-write + remount test, which is not practical in this
  container environment.
- **Real Hunter SE hardware** was never available in this environment (a
  pre-existing, disclosed limitation of the whole package, unrelated to
  this pass -- see `docs/DELIVERY_REPORT.md`).
